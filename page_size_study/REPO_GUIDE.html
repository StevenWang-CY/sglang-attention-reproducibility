0一句话概述 & 全景

先建立全局直觉，再逐层下钻。整个仓库其实在回答一个核心问题。

💡 核心洞察（贯穿全仓库）
智能体浏览器的提示词 = ChatML 角色结构 + HTML/DOM 可访问性树 + 多步 agent 历史， 动辄上万 token 且 高度结构化。既然输入是「树」，那么模型对它的注意力大概率也是 稀疏且沿结构分布 的—— 于是：(A) 先把注意力可视化看清楚 → (B) 用树结构做稀疏注意力把推理加速 → (C) 严谨测量延迟验证收益。
看见注意力可视化

把 Qwen3-VL 对浏览器 DOM 的注意力 dump 成 CSV，渲染为火焰图 / 热力图 / 结构树，定位「模型在看哪些元素」。

加速Tree-Sparse 后端

自研 SGLang 注意力后端：按 ChatML/HTML 树切块 → 质心相似度选 Top-K 块 → 只对选中块做精确注意力。

量化延迟测量基建

离线 Engine + 在线 HTTP 双路测 TPOT/TTFT/ITL，配合 nsys/ncu/PyTorch Profiler 做 kernel 级剖析。

1研究动机与真实场景

所有实验都围绕同一个标定工作负载（workload）展开：一个浏览器智能体在 Hacker News 上找第 50 个帖子。

📥 标定输入 · html_request/request_005_…/request.json

一个真实的 agentic browser 推理请求，结构为 2 条 ChatML 消息：

system16,623 字符agent loop 规则、动作格式、文件系统用法
user11,955 字符agent_history + agent_state + browser_state(DOM)

分词后 ≈ 9,661 tokens。模型：Qwen3-VL-30B-A3B-Instruct。

🎯 任务 · <user_request>

# 真实任务
Find the number 50 post on
https://news.ycombinator.com/

# agent_history 里记录了多步
<step> Navigated to news.ycombinator.com
<step> Scrolled down 1080px  (×4)
<browser_state> ...DOM 可访问性树...

这类提示词的特点：长、重复、强结构——正是稀疏注意力的理想猎物。

为什么「智能体浏览器」值得专门优化？

特征数值/表现推理意义
上下文长度10K–40K+ tokens / 请求解码每步都要重读巨大 KV cache → 带宽瓶颈
结构化程度ChatML + HTML + DOM 树天然可切成语义块（chunk），便于稀疏选择
多步循环agent_history 不断增长大量历史 token 注意力极低 → 可裁剪
批量并发batch 1 → 64（618K tokens）批越大越「attention-bound」，page/稀疏更关键

关键测量指标 TPOT（Time Per Output Token，每输出 token 的纯解码延迟，排除 prefill）贯穿所有性能实验，定义见 measure_batch_latency_offline.py:304。

4.3 关键发现：注意力到底在看什么？

来自 ANALYSIS_SUMMARY.md + tree_persistence_analysis.txt（统计 113 个生成 token，8426–8650）。下表为「在 100% 的生成步里持续高注意力」的元素 Top 榜：

排名区间类别累计注意力占比可视含义
1[8420:8652]assistant77.83正在生成的回复（自注意力）
2[8423:8516]Text39.48输出 JSON 的 "thinking" 字段
3[3577:8419]user27.40整个 user 上下文
4[3999:8417]browser_state24.00浏览器状态区
5[4136:8400]html_root19.41<html /> 根元素
9[0:3576]system7.77系统提示（稳定背景）
✅ 结论
① 大部分注意力给了「正在生成的输出本身」（77.8，自注意力主导）；② browser_state 重要（24.0）但弱于生成区；③ 具体搜索结果（article/li 元素）保持稳定重要性；④ "thinking" 字段方差最大（每步关注点不同）。
而「<browser_state> 父节点 0.703 vs 子节点 0.554 之间缺失的 0.15」并非 bug——它分散在结构性 gap token（标签、换行、Tab）与子层级递归 gap 中。由 analyze_browser_state_detail.py、find_heavy_gaps.py、show_uncaptured_tokens.py 逐 token 验证。

5主线 B · Tree-Sparse 注意力（核心创新）

一个自研的 SGLang 注意力后端：利用输入的结构层级（ChatML / HTML / DOM）把 KV cache 切成语义块，再用质心相似度每层独立挑 Top-K 块，使 prefill 与 decode 都变成亚二次复杂度。

5.1 三大组件

tree_parser.py

把扁平 token 序列解析成 ChatML/HTML 树 → 提取叶子 FlatChunk（填 gap、合并小块 <16、拆大块 >256）。解析失败回退定长块。

centroid_manager.py

存每请求/每层的块质心（mean key 向量）。prefill 用 mean(x)@W_k 优化算；decode 用 running-mean 增量更新。

sparse_selector.py

query·centroid 点积打分 → Top-K 选块 → 构造 FlashInfer 稀疏 KV 索引（CSR 格式 kv_indptr/kv_indices）。

🔑 每层独立选块：第 0 层可能盯 system，第 30 层可能盯最近输入——因为每层有自己的质心。代价是 decode 每层都要 begin_forward 重规划（故需 --disable-cuda-graph）。

5.3 数学优化：为什么质心能「先平均再投影」

# 朴素：每个 token 投影后再平均（n 次投影）
centroid = mean({ x_i @ W_k })

# 优化：先平均 hidden，再投影一次（1 次投影）
x_bar    = mean({ x_i })       # 便宜
centroid = x_bar @ W_k         # 只投影质心

# 因矩阵乘线性，二者严格相等：
mean(x_i @ W_k) = (mean x_i) @ W_k  ✓

收益（10K token / 100 块）

质心投影次数10,000 → 100
等价性严格相等
测试test_centroid_
optimization.py

由 CENTROID_OPTIMIZATION_INTEGRATED.md 记录；模型层 qwen3.py 从融合 qkv 权重切出 W_k 经 **kwargs 传给后端。

6主线 C · Page-Size 延迟研究

研究问题：KV-cache 的 page_size=1 什么时候「不是」最低延迟？ 这是一份方法论严谨、含测量卫生（measurement hygiene）的完整实验报告（PAGE_SIZE_LATENCY_REPORT.md）。

两个测量层级，结论相反

孤立 kernel 微基准 benchmark_page_size_attention.py：在 attention-bound（大 batch×长 KV）区，page_size=1 不是最低——5060 Ti 上 16/16 格、数据中心 11/12 格更大 page 略胜（但差距极小）。

完整 SGLang 引擎 measure_batch_latency_offline.py：在 16GB 5060 Ti 上，page_size=1 在每个 batch 都最低——大 page 因「页内碎片/尾部过读」反而更慢。

效应有多大？（都 ≤ 几个百分点）

层级/硬件page=1 罚分
孤立 kernel · 5060Ti中位 0.27% / max 1.08%
孤立 kernel · 数据中心中位 1.37% / max 3.26%
引擎 · 5060Ti bs=8page=1 反胜 +0.77%
引擎 · 5060Ti bs=16page=1 反胜 +1.18%
✅ 最终回答
存在这样的场景：attention-bound 的孤立 decode 注意力 kernel 里，更大的 page（8–64）以微弱优势胜过 page_size=1。但在 16GB GPU 的完整引擎里没找到——碎片惩罚压过了合并收益。实践含义：page size 对单卡解码延迟是个近乎中性的旋钮，应为内存效率而非速度去选它。
🔬 测量卫生（体现严谨性）
早期「bs=1/kv=1024 下 page=1 慢 2.2×」被识破为 cold-start 伪影（新进程首个 kernel 启动开销），warm 重测后 ~56µs 全平，已剔除。另有 #running-req 日志格式不匹配导致的假警报也已澄清（TPOT 从 batch 8→16 翻倍证明确实并发）。

报告配图（report_assets/，本地打开可见）

相关微基准：bench_kv_access.py（连续 vs 分页 KV 访问，含 L2 flush）、benchmark_memory_access.py（带宽随访问步长退化）。数据：page_size_attn_bench.json(数据中心)、page_size_attn_bench_5060ti.json。

7主线 D · QKV 计时异常调查

一桩「侦探案」：当 batch 从 16→32，QKV 投影计时不升反降 63%。仓库用尽各种无需 admin 权限的取证手段，最终给出 90% 置信的解释。

🧩 异常现象（可复现）

batch 16batch 32
总时间20.81 ms27.80 ms
QKV 时间1.60 ms0.59 ms
预期 QKV—~3.20 ms

~2.61 ms「凭空消失」。但总时间在涨，工作并没有变少。

🔎 证据链

  • 不同 kernel：batch 16/32 的 nvjet_tst_* GEMM tile 宽度翻倍（8→16, 16→32），由 NVIDIA JIT 按 batch 自适应。
  • 插桩对比：wall-clock（仅捕获 Python 启动开销）≪ CUDA event（真实 GPU 时间），因 kernel 异步启动。
  • 权限墙：ncu 报 ERR_NVGPUCTRPERM（无 GPU 性能计数器权限），nsys/PyTorch Profiler 只能拿到高层 API。
🧠 假说（90% 置信）
batch=32 切换到不同的 nvjet kernel，这些 kernel 绕过了 tree-sparse 的计时插桩点，导致计时少报而非真的变快——是「插桩盲区」，不是性能提升。要 100% 证实需 admin 开 NVreg_RestrictProfilingToAdminUsers=0，或在 SGLang 源码 GEMM 调用处加 CUDA event（见 SOURCE_INSTRUMENTATION_GUIDE.md）。

取证工具矩阵：analyze_qkv_anomaly.py（4 联图）·analyze_kernel_diff.py / analyze_all_kernel_profiles.py（ncu CSV diff）·analyze_pytorch_traces.py（Chrome trace）·instrument_kernel_selection.py（monkey-patch F.linear）·patch_sglang_logging.py（改源码加日志）·cuda_intercept.c（LD_PRELOAD 拦截 cudaLaunchKernel）。

8主线 E · 测量 & Profiling 基础设施

支撑前四条主线的「地基」：一套从端到端 TPOT 到 kernel 级 DRAM 字节的多层测量体系。

8.1 核心测量器 · measure_batch_latency_offline.py（~29KB）

直接用 in-process sglang.Engine（无 HTTP 开销）测真实 TPOT。流式拿首 token 时间，区分 prefill/decode。

指标定义
TPOT(total_time − TTFT) / (tokens − 1)　纯解码，排除 prefill
TTFT首 token 时间（≈ prefill 延迟）
Throughputbatch × tokens / total_time

11关键发现汇总

把五条主线的结论收敛成一张「结论卡」。

A · 注意力结构

生成区自注意力主导（77.8）；browser_state 重要但次之（24.0）；"thinking" 字段方差最大；system 提示稳定低注意力。「缺失的 0.15」是结构 gap token，非 bug。

B · Tree-Sparse

可把每步注意力从 ~10,000 token 降到 ~932 token；质心「先平均后投影」省 ~100× 投影且严格等价。代价：每层重规划、无 CUDA graph、选块本身有开销。

C · Page-Size

page size 对单卡解码延迟近乎中性（≤ 几个百分点）。孤立 kernel 里大 page 微胜；16GB 引擎里 page=1 反胜（碎片惩罚）。为内存效率选它，不为速度。

D · QKV 异常

batch=32 QKV 计时降 63% 是插桩盲区（JIT 换了 nvjet kernel 绕过计时点），非真加速。90% 置信，缺 admin 权限无法 100% 实证。

🧭 方法论亮点（值得学习）
本仓库的可贵之处在于测量诚实：主动识别并剔除 cold-start 伪影、澄清日志格式导致的假警报、在拿不到 admin 权限时明确区分「已证实 / 强推断 / 无法证明」三档置信度，并给出升级到确证所需的具体步骤。
