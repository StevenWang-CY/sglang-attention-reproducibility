# KV-cache `page_size` (block_size) vs decode latency — study index

**Research question:** find a scenario where KV-cache `page_size=1` is **not** the lowest-latency choice, by ≥5% (PI: Jiaheng Lu). Engine: SGLang (+ a vLLM cross-check). Hardware: RTX 5060 Ti (16 GB, sm120) on `gray.cis.upenn.edu`, with H100/B200 reference data where noted.

Everything new from this study lives under `page_size_study/`. **Each report sits in its own directory together with the PNG figures it uses.** The large raw result dirs stay in their canonical (gitignored) location `offline_batch_results/`, catalogued in **[DATA_INDEX.md](DATA_INDEX.md)**.

**Headline finding** (report 3): on Triton, `page_size=1` loses **+15–40%** to `page_size=128` at high batch + shared prefix — every model tested, even with CUDA graph ON; magnitude tracks **layer count**, not KV/token. FlashInfer is far more robust but **not immune** (report 4: a narrow long-context corner). vLLM can't even express the pathology (it disallows `block_size < 16`). **Crucial scope (report 5):** this whole effect is **shared-prefix-specific** — in a *true* batch (independent sequences, `bench_one_batch`) `ps1` is the **fastest** page at every batch and context, both backends; the ≥5% penalty disappears. An **adversarial break-search** (FlashInfer+graph: batch→512, L2-resident KV, long single-seq, GQA-2 model) confirms it: **no** true-batch `ps1` penalty exists (max +0.2% across 19 cells). **Hardware-counter grounding (report 6):** ncu profiling of the modern **XQA** kernel (`kernel_mha`) on sm120 shows it uses **no TMA** (cp.async/LDGSTS, like FlashInfer) and decode is **DRAM-bandwidth-bound (~95% peak)** — so page_size and kernel choice are second-order; XQA only supports page≥16. An **extensive sm120 TMA survey** (report 6) finds TMA is emitted **only by CUTLASS-Blackwell GEMM** kernels (e.g. FlashInfer's cutlass fp8 GEMM — 134 MB TMA, verified positive control) — while **no attention kernel** (XQA / FlashInfer / FlashAttention) uses TMA, and cuBLAS/cuDNN GEMM fall back to Ampere/Ada kernels. **Root cause of the shared-prefix gap (report 7):** ncu (controlled shared-vs-distinct KV) shows a shared prefix flips decode from **DRAM-bandwidth-bound** (true batch: ~95% peak DRAM, ~0% L2 reuse) to **L2-cache-bound** (~90% L2-hit, ~3× faster) — the page access pattern is hidden behind the bandwidth wall in a true batch (so `ps1` is free), and only becomes a first-order cost when the KV is cache-resident (shared), which is where Triton's `ps1` +11–25% lives. **Can you escape the wall the *other* way — by shrinking the KV (report 8)?** No: in a true batch decode stays DRAM-bound even with small KV — the **model weights** (4.10 GB/step) dominate the engine's DRAM traffic at small ctx, and ncu (cold) shows a small *distinct* KV is still streamed from HBM at 79→96% of peak (each layer re-fetches it every step; the 32 MB L2 is thrashed between layers). Genuine cache-residency in decode requires cross-sequence **reuse** (a shared prefix), not a small footprint — and even in the one (isolated-loop) regime where small KV does go resident, FlashInfer's page-agnostic kernel keeps `ps1`≈`ps128` (≤+0.8%). So `page_size=1` is never ≥5% slow in a true batch, large KV **or** small. **Decisive closure (report 10):** reading the actual `sglang_CW` source shows that for FlashInfer decode the KV pool is token-flat and the `kv_indices` list is **per-token, length `B·ctx`, independent of `--page-size`** (with `page_size` hard-coded to 1 into the plan) — so `--page-size` changes only the *value contiguity* of `kv_indices`, not the index length or the plan. Pushed to the extreme (B8×L131072 = 1.05M entries): the per-step host `plan()` is **flat ~0.26 ms** regardless of length, and worst-case **scattered** indices (maximal ps1 fragmentation) cost the kernel only **+0.8–1.3 %** (ncu: contig≈scatter at 96 % DRAM, identical 15.6 sectors/request — a token's 4 KB KV read coalesces the same way regardless of ordering). So there is **no** {graph ON + FlashInfer + distinct} cell where `ps1` is notably worse, by host **or** kernel path; the report-4 +8.6 % is not a decode-path page cost in this build. **The one case report 10 left open — MLA — is closed by report 10's sibling, report 11:** MLA decode (1152 B/token latent, *off the DRAM wall* via cross-head reuse) is the most page-sensitive distinct-KV case found, yet worst-case scattered `ps1` **saturates at +4.07 % and never reaches 5 %** (ncu: `sectors/request` unchanged — not coalescing; DRAM only 15–38 % — latency-bound, so scattered-page DRAM latency shows but is bounded), and realistic `block≥64` paging is free. **Final rule across MHA/GQA *and* MLA: a ≥5 % `ps1` decode penalty is reuse-gated (shared prefix), never produced by footprint, per-token burst size, batch, context, or fragmentation.**
